# 맵 개편 + 캐릭터 정보/인벤토리 설계

- 작성일: 2026-10-08
- 대상: 본 이야기 + 반복 파밍 맵, 파티 정보 화면, 인벤토리와 장비 장착
- 선행 문서: `2026-09-16-map-prototype-design.md` (전투와 맵의 연결 구조는 그대로)
- 와이어프레임: Figma `Game UI Wireframes` 파일의 `v3 · 와이어프레임` 페이지 (03 월드맵, 09 사원 명부, 10 창고)

## 1. 범위

복잡도를 낮추기 위해 이번에는 세 가지만 다룬다.

1. **맵**: 슬레이 더 스파이어식 랜덤 그래프를 "본 이야기 일직선 + 이야기 노드마다 옆으로 매달린 반복 파밍 노드" 구조로 교체한다.
2. **캐릭터 정보**: 파티원의 능력치, 장비, 덱을 보여 주는 화면.
3. **인벤토리**: 아이템 보유 목록, 상세 보기, 장착·해제, 전투 승리 시 아이템 획득.

제외: 상점·휴식·이벤트 노드, 세이브·로드, 아이템 등급·강화, 캐릭터 레벨·경험치, 파티 편성(출전 인원 선택). 전투 규칙(`Scripts/combat/`)은 한 줄도 바꾸지 않는다.

## 2. 맵

### 2.1 구조

```
        파밍 ─┐     ┌─ 파밍
보스 ─ 이야기5 ─ 이야기4 ─ … ─ 이야기1 ─ 시작
```

- `MapNode.Kind`: `START`, `STORY`, `FARM`, `BOSS`. `row`는 세로 위치, `col`은 이야기 길(0) 기준 좌우 오프셋, `parent_id`는 파밍 노드가 매달린 이야기 노드.
- `MapGraph`: 이야기 노드 `STORY_COUNT`(5)개 + 보스. 이야기 노드마다 파밍 노드 `FARM_MIN`~`FARM_MAX`(1~2)개. 2개면 양옆(-1, +1), 1개면 랜덤한 한쪽. `connections`는 `[다음 이야기 노드, 파밍 노드들...]` 순서다.
- 상수와 모양은 플레이하며 조정할 출발값이다.

### 2.2 진행 규칙 (`MapRunState`)

| 항목 | 규칙 |
|---|---|
| 이야기 노드 | 현재 이야기 노드의 다음 노드만 선택 가능. 깨면 `current_node_id`가 옮겨가고 `cleared`에 들어간다. 다시 들어갈 수 없다. |
| 파밍 노드 | 부모 이야기 노드를 깬 뒤부터 몇 번이든 선택 가능. 깨도 `current_node_id`와 `cleared`는 변하지 않는다. 앞 이야기 노드의 파밍도 계속 열려 있다. |
| 적 구성 | 이야기·보스는 지도 생성 때 정해져 다시 도전해도 같다. 파밍은 들어갈 때마다 새로 뽑는다. |
| 보스 클리어 | 새 지도(다음 챕터)를 만든다. 파티와 인벤토리는 유지한다. |
| 패배 | 지도·파티·인벤토리 모두 유지하고 다시 도전할 수 있다. (이전 프로토타입은 런을 초기화했다.) |

`encounter_for(node_id, ally_units)`는 아군 배치를 인자로 받는다. 장비가 전투 직전까지 바뀔 수 있기 때문이다.

## 3. 파티와 인벤토리

### 3.1 데이터

- `ItemData` (`Scripts/party/item_data.gd`, Resource): `id`, `display_name`, `slot`(무기/방어구/장신구), `description`, 보너스 `max_hp_bonus`, `speed_bonus`, `max_sp_bonus`, `attack_bonus`. 아이템은 `Resources/items/*.tres`에 둔다.
- `ItemPool`: 폴더의 아이템을 파일 이름순으로 불러오고(시드 재현성), 시드 있는 rng로 하나를 뽑는다.

### 3.2 규칙 코어 (`PartyState`, RefCounted)

- 파티원은 `EncounterGenerator.build_ally_roster`가 만든 `UnitPlacement`(복제된 `AllyData` + 칸)이다.
- `inventory`는 가방(같은 아이템 여러 개 가능), 장착은 파티원 번호별 `{부위 -> ItemData}`.
- `equip(index, item)`: 가방에 있는 아이템만 장착된다. 같은 부위에 낀 아이템은 가방으로 돌아간다. `unequip(index, slot)`은 가방으로 되돌린다.
- `stats(index)`: 기본 능력치 + 장비 보너스. 체력·속도·SP는 최소 1.
- `build_battle_roster()`: **전투 코드를 바꾸지 않기 위한 연결점.** 원본을 건드리지 않고 `AllyData` 복사본에 최종 체력·속도·SP를 넣고, `attack_bonus`만큼 **피해가 있는 카드**를 복사해 피해량을 올린다(같은 카드는 같은 복사본을 공유).
- 바뀔 때마다 `changed`를 낸다.

### 3.3 화면 (`PartyView`, `Scripts/ui/party_view.gd`)

코드로 구성하는 전체 화면 `Control`(MapView와 같은 방식).

- 왼쪽: 파티원 버튼 목록. 가운데: 초상, 이름, 능력치(보너스는 `(+3)`로 표기), 덱 요약. 오른쪽: 장비 슬롯 3개(누르면 해제), 인벤토리 격자(누르면 선택), 상세, `장착` 버튼.
- 아이템을 고르면 설명·보너스를 보여 주고, 같은 부위에 낀 아이템이 있으면 교체 안내를 띄운다.
- `PartyState.changed`를 받아 다시 그린다.

## 4. 연결 (`GameRoot`)

- 시작 시 `PartyState`를 만들고 아이템 3개를 가방에 넣는다.
- 지도 오른쪽 위 `파티 · 인벤토리` 버튼 → `PartyView` 표시(지도 숨김), `닫기` → 지도 복귀.
- 전투 시작 시 `run_state.encounter_for(node_id, party.build_battle_roster())`.
- 승리 시 `ItemPool.roll`로 아이템 하나를 인벤토리에 넣고 지도에 `획득: …` 배너를 띄운다. 이야기 노드든 파밍 노드든 동일하다.

## 5. 테스트

- `test_map_graph` / `test_map_layout` / `test_map_run_state` / `test_map_view`: 새 구조에 맞게 다시 썼다.
- `test_item_data`: 아이템 요약, 풀 로딩(id 유일, 3부위 모두 존재), 시드 재현.
- `test_party_state`: 장착·교체·해제·복수 보유, 능력치 합산과 하한, 전투 로스터 반영과 원본 보존, `changed` 시그널.
- `test_party_view`: 목록·선택·장착·해제·교체 안내·닫기·파티 변경 반영.
- 통합은 `GameRoot`를 헤드리스로 띄워 지도 → 파티 → 장착 → 전투 시작(보너스 반영) → 승리 보상 → 파밍 → 패배까지 수동 스크립트로 확인했다.

## 6. 미결정 / 다음 단계

- 아이템 효과는 체력·속도·SP·피해뿐이다. 방어도, 사거리 같은 효과는 전투 규칙 변경이 필요해서 뺐다.
- 파밍 노드의 난이도·보상은 일반 노드와 같다. 반복 파밍의 보상 설계는 다음 이터레이션.
- 파티 편성(4명 중 출전 선택), 레벨·경험치, 세이브·로드.
- 와이어프레임의 사무소 허브, 카드 공방(덱 편집), 의뢰 정보 패널은 아직 구현하지 않았다.
