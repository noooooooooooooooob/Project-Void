# 전투 프로토타입 설계

- 작성일: 2026-09-12
- 대상: Project Void 전투 시스템 최소 핵심 루프
- 상태: 승인 대기

## 1. 배경

Project Void는 턴제 덱빌딩 로그라이크다 (레퍼런스: 고디안 퀘스트, 카제나, 니드파이어, 알리나 오브 더 아레나, 아스트레아). 노션 기획서에 전투 시스템이 진영 타일, 카드, 궁극기, 디버프, 장비, 던전까지 폭넓게 정리돼 있지만 코드는 아직 한 줄도 없다.

이 문서는 그 중 **최소 핵심 루프만** 잘라내어 실제로 플레이 가능한 전투를 만드는 설계다. 목적은 규칙이 재미있는지, 그리고 구조가 이후 확장을 버티는지 확인하는 것이다.

## 2. 범위

### 포함

- 가변 크기 진영 그리드 (아군 좌 / 적군 우)
- 이니셔티브(속도) 기반 턴 진행
- **아군**: 덱 / 손패 / 묘지 / 제외 존과 드로우·리셔플, 유닛별 SP, SP가 허용하는 한 카드 자유 사용
- **적군**: 카드를 쓰지 않는다. 공격 / 방어 / 휴식 3종 행동 세트
- 카드 5종: 근접/원거리 × 단일/광역
- 사거리 판정과 근접 관통 불가(전열 블로킹) 규칙 — 아군 카드와 적 공격에 동일 적용
- 방어로 얻는 `block` (받는 데미지 흡수)
- 규칙 전체를 덮는 헤드리스 테스트
- 최소 2D UI (플레이 가능한 수준)

### 제외 (다음 이터레이션)

장비, 궁극기 게이지, 디버프/상태이상, 어그로, 아이템, 발라트로식 카드 증강, 이동 카드, 아군/자신/논타겟 카드, 던전·노드 맵, 2.5D Sprite3D 표현, 특성.

제외 항목 중 **제외(exile) 존**만 예외적으로 자료구조를 미리 만든다. 나중에 소모성 카드·증강이 들어올 자리인데 나중에 끼워 넣으면 존 이동 로직을 전부 다시 건드려야 하기 때문이다. 이번 스코프에서 제외 존으로 가는 카드는 없다.

## 3. 아키텍처

3계층으로 나눈다.

```
┌──────────────────────────────────────────────┐
│  표현 레이어   BattleScene.tscn               │
│               battle_controller.gd (Node)     │
│   입력 → 규칙 호출, 상태 변화 → 화면 갱신      │
└───────────────────┬──────────────────────────┘
                    │ (단방향 의존)
┌───────────────────▼──────────────────────────┐
│  규칙 코어 (RefCounted, Node 의존 없음)        │
│   BattleState / Unit / TargetResolver /      │
│   EnemyBrain                                 │
└───────────────────┬──────────────────────────┘
                    │
┌───────────────────▼──────────────────────────┐
│  데이터 (Resource, .tres)                     │
│   CardData / UnitData / EncounterData        │
└──────────────────────────────────────────────┘
```

규칙 코어에 Node 의존을 두지 않는 이유는 두 가지다. 첫째, 씬을 띄우지 않고 헤드리스로 규칙을 테스트할 수 있다. 둘째, 노션 기획의 증강·디버프·장비가 나중에 들어올 때 표현 레이어를 건드리지 않고 규칙만 확장할 수 있다.

카드/유닛 정의를 `Resource`로 두는 이유는 기획자가 코드 대신 Godot 인스펙터에서 카드를 추가·수정할 수 있게 하기 위해서다.

**만들지 않는 것:** 범용 효과 큐 엔진. 지금 카드 효과는 "대상에게 데미지" 하나뿐이라 엔진을 세우면 과설계다. 효과 종류가 3개를 넘어가는 시점에 도입한다.

## 4. 좌표계와 그리드

각 진영은 독립된 그리드를 가지며 **크기가 서로 달라도 된다**.

- 진영 그리드: `cols × rows`
- 유닛 위치: `Vector2i(col, row)`
- **col 0 = 최전열** (적 진영과 가장 가까운 열). col이 커질수록 후방.

col 0을 전열로 고정하는 이유는 진영 크기가 달라도 "전열"의 정의가 흔들리지 않게 하기 위해서다. 화면상 아군은 좌측이라 col 0이 시각적으로는 오른쪽 끝에 오는데, 이 미러링은 **표현 레이어에서만** 처리하고 규칙 코어는 언제나 로컬 좌표로만 계산한다.

```
   아군 진영 (3열 x 3행)          적군 진영 (2열 x 2행)
   col2  col1  col0              col0  col1
  ┌────┬────┬────┐              ┌────┬────┐
  │    │    │ A1 │  row0        │ E1 │    │  row0
  ├────┼────┼────┤              ├────┼────┤
  │    │ A2 │    │  row1        │    │ E2 │  row1
  ├────┼────┼────┤              └────┴────┘
  │ A3 │    │    │  row2
  └────┴────┴────┘
        ←── 전열 방향        전열 방향 ──→
```

## 5. 거리와 타겟팅

### 5.1 횡거리

```
col_distance(a, b) = a.col + 1 + b.col
```

두 진영 사이 간격을 1로 본다. 양쪽 최전열끼리는 `0 + 1 + 0 = 1`.

### 5.2 종거리 (중앙 정렬)

진영의 행 수가 다를 수 있으므로 가운데를 기준으로 맞춘다.

```
center_offset(row, rows) = row - (rows - 1) / 2.0
row_distance(a, b)       = roundi(abs(center_offset(a) - center_offset(b)))
```

행 수가 둘 다 홀수거나 둘 다 짝수면 오프셋 차이는 항상 정수다. 한쪽만 홀수일 때만 0.5 단위가 생기고, 이때는 `roundi`가 올려서 보수적으로(더 먼 쪽으로) 판정한다. `roundi(0.5) == 1`.

예 — 아군 3행 vs 적군 5행:

| 아군 row | 오프셋 | 적군 row | 오프셋 | 종거리 |
|---|---|---|---|---|
| 0 | -1.0 | 2 | 0.0 | 1 |
| 1 | 0.0 | 2 | 0.0 | 0 (정면) |
| 2 | +1.0 | 3 | +1.0 | 0 (정면) |

### 5.3 사거리 판정

```
reach(a, b) = col_distance(a, b) + row_distance(a, b)
도달 가능   = reach(a, b) <= card.range
```

### 5.4 근접 블로킹 (관통 불가)

근접 카드는 **타겟이 자기 행의 최전방 생존 유닛일 때만** 지정할 수 있다.

```
is_blocked(target) = 타겟과 같은 진영, 같은 row에,
                     target.col 보다 작은 col을 가진 생존 유닛이 하나라도 있으면 true
```

공격자의 행은 이 판정에 관여하지 않는다. 사거리만 닿으면 대각선 방향의 적 전열도 칠 수 있다.

원거리 카드는 블로킹을 무시하고 사거리만 검사한다.

### 5.5 광역 패턴

**1차 타겟**은 플레이어(또는 AI)가 지정한 셀 하나를 말한다. 패턴은 1차 타겟을 기준으로, **1차 타겟이 속한 진영 안에서만** 퍼진다.

| shape | 범위 | 축 |
|---|---|---|
| `SINGLE` | 1차 타겟만 | — |
| `PIERCE` | 1차 타겟과 **같은 row**의 모든 생존 적 | 진영 깊이 방향 (전열→후열 관통) |
| `SWEEP` | 1차 타겟과 **같은 col**의 모든 생존 적 | 전열을 따라 좌우 확산 |

`ROW`/`COLUMN` 대신 `PIERCE`/`SWEEP`으로 이름 붙인 이유는, 이 그리드에서 "행"과 "열"이 화면상 방향과 반대로 읽히기 쉬워서다 (같은 row = 화면상 가로 = 진영 깊이, 같은 col = 화면상 세로 = 전열 폭). 이름이 하는 일을 직접 가리키게 해서 구현 중 축을 헷갈리는 사고를 막는다.

사거리 검사와 근접 블로킹 검사는 **1차 타겟에만** 적용한다. 1차 타겟이 합법이면 패턴이 퍼진 나머지 칸은 추가 검사 없이 맞는다. 이렇게 하지 않으면 광역 근접 카드가 사실상 전열 1칸만 때리게 되어 광역의 의미가 없어진다.

## 6. 턴과 라운드

```
전투 시작
  └─> 라운드 시작
        ├─ 이니셔티브 순서 계산
        │    생존 유닛 전체를 speed 내림차순 정렬,
        │    동점은 unit_id 오름차순 (결정론 보장)
        │
        └─> 각 유닛 차례 (순서대로)
              ├─ 공통 차례 시작: block 을 0 으로 초기화
              │
              ├─ 아군이면
              │    ├─ SP를 max_sp로 회복, DRAW_PER_TURN(=4)장 드로우
              │    ├─ SP가 허용하는 한 카드 자유 사용 (플레이어 입력)
              │    └─ 차례 종료: 손패 전부 묘지로
              │
              ├─ 적군이면
              │    └─ 공격 / 방어 / 휴식 중 하나를 골라 1회 실행 (EnemyBrain)
              │
              └─ 승패 확인
        └─ 다음 라운드
```

아군과 적군의 차례 구조가 다르다. 적은 카드도 SP도 손패도 갖지 않고, 자기 차례에 정해진 행동 하나만 한다.

이니셔티브 순서는 라운드 시작 시점에 한 번 계산하고 그 라운드 동안 고정한다. 라운드 도중 유닛이 죽으면 그 유닛의 차례는 건너뛴다.

낼 수 있는 카드가 없는 차례(SP 부족이거나 유효 타겟이 없음)도 정상 상태다. 플레이어는 언제든 "차례 종료"를 누를 수 있고, AI는 후보가 비면 즉시 차례를 넘긴다.

드로우 매수는 `DRAW_PER_TURN` 상수로 둔다. 현재 값은 4이고 유닛별 차등은 두지 않는다 — 특성 시스템이 들어오는 다음 이터레이션에서 유닛 스탯으로 승격할 자리다.

**승패:** 한쪽 진영의 생존 유닛이 0이 되면 즉시 종료. 카드 해결 직후마다 검사한다.

## 7. 카드와 덱 (아군 전용)

카드 시스템은 **아군 유닛에만** 적용된다. 적은 덱도 손패도 SP도 갖지 않는다 (8장 참조).

### 7.1 존

아군 유닛마다 4개의 존을 가진다. 덱은 유닛별로 분리되어 있다 (노션: "각 정화자는 고유 카드덱 보유").

| 존 | 성격 |
|---|---|
| 덱 (draw pile) | 순서 있음. 맨 앞에서 뽑는다 |
| 손패 (hand) | 현재 차례에 쓸 수 있는 카드 |
| 묘지 (discard) | 사용했거나 버려진 카드 |
| 제외 (exile) | 이번 스코프에서는 아무것도 들어가지 않음 |

### 7.2 드로우

```
draw(n):
  n 번 반복:
    덱이 비었으면:
      묘지가 비었으면 -> 중단 (더 못 뽑음)
      묘지를 셔플해서 덱으로 전부 옮기고 묘지를 비움
    덱 맨 앞 카드를 손패로
```

### 7.3 차례 종료

손패에 남은 카드는 **전부 묘지로** 간다. 다음 차례로 들고 가지 않는다.

### 7.4 결정론

셔플과 드로우는 `BattleState`가 보유한 주입된 `RandomNumberGenerator`를 사용한다. 테스트에서 시드를 고정할 수 있어야 하고, 그래야 덱 관련 버그를 재현할 수 있다. 전역 `randi()`를 직접 호출하는 코드는 금지한다.

## 8. 적 행동과 block

적은 카드를 쓰지 않는다. 자기 차례에 **공격 / 방어 / 휴식** 중 하나를 골라 한 번 실행한다.

### 8.1 행동 3종

| 행동 | 효과 |
|---|---|
| 공격 | `EnemyData`에 정의된 고정 공격 1회. 타겟팅은 아군 카드와 **동일한** 규칙(사거리, 근접 블로킹, 광역 패턴)을 따른다 |
| 방어 | `block_amount` 만큼 block 획득 |
| 휴식 | `rest_heal` 만큼 HP 회복 (max_hp 초과 불가) |

적 공격도 `TargetResolver`를 그대로 쓴다. 적 전용 타겟팅 규칙을 따로 두면 그리드가 적 입장에서 의미를 잃고, 규칙이 두 벌로 갈라져 서로 어긋난다.

### 8.2 block

- 받는 데미지는 **block이 먼저 흡수**하고 남은 만큼만 HP를 깎는다. 흡수한 만큼 block이 줄어든다
- block은 **자기 차례 시작 시 0으로 초기화**된다. 방어로 얻은 block은 자기 다음 차례가 돌아올 때까지 유지된다
- 아군도 `block` 필드를 갖지만 현재 카드셋에 block을 주는 카드가 없어 항상 0이다. 데미지 처리 경로를 한 벌로 유지하려고 필드는 공통으로 둔다

### 8.3 행동 선택 (결정론)

```
HP 비율이 REST_THRESHOLD(=30%) 이하이고 rest_heal > 0  ->  휴식
그렇지 않고 유효 공격 타겟이 하나도 없으면              ->  방어
그 외                                                  ->  공격
                                                           (HP 최소 유효 타겟,
                                                            동점은 unit_id 오름차순)
```

무작위성을 넣지 않는다. 테스트에서 적 턴 결과를 단정할 수 있어야 하기 때문이다. 세 행동 모두 실제로 발동할 조건이 있어야 의미가 있으므로, 휴식은 체력이 깎였을 때, 방어는 때릴 대상이 없을 때(사거리 밖이거나 전열에 막혔을 때) 나오게 했다.

이건 **임시 규칙**이다. 노션 기획의 적 설계(어그로, 패시브, 디버프)가 확정되면 통째로 교체된다.

## 9. 데이터 모델

```gdscript
# CardData.gd  (Resource)
enum AttackType { MELEE, RANGED }
enum Shape { SINGLE, PIERCE, SWEEP }

id: StringName
display_name: String
sp_cost: int
attack_type: AttackType
shape: Shape
range: int
damage: int
```

아군과 적군은 가진 것이 달라서 데이터도 나눈다. 공통분을 베이스로 두고 각자 확장한다.

```gdscript
# UnitData.gd  (Resource)  — 공통 베이스
id: StringName
display_name: String
max_hp: int
speed: int
```

```gdscript
# AllyData.gd  (UnitData 상속)
max_sp: int
deck: Array[CardData]      # 같은 카드를 여러 장 넣을 수 있음
```

```gdscript
# EnemyData.gd  (UnitData 상속)  — 카드를 쓰지 않는다
attack_damage: int
attack_type: CardData.AttackType   # MELEE / RANGED
attack_shape: CardData.Shape       # SINGLE / PIERCE / SWEEP
attack_range: int
block_amount: int                  # 방어 시 얻는 block
rest_heal: int                     # 휴식 시 회복량
```

공통 필드를 억지로 한 클래스에 몰고 `deck`을 빈 배열로 두는 방법도 있지만, 그러면 "적은 카드를 쓰지 않는다"가 타입이 아니라 관례로만 남아서 나중에 실수로 적에게 덱을 물릴 수 있다. 타입으로 갈라두면 컴파일 단계에서 막힌다.

```gdscript
# EncounterData.gd  (Resource)   — 전투 하나의 셋업
ally_grid: Vector2i        # (cols, rows)
enemy_grid: Vector2i
ally_units: Array[UnitPlacement]
enemy_units: Array[UnitPlacement]

# UnitPlacement.gd  (Resource)
unit_data: UnitData
cell: Vector2i             # (col, row), 로컬 좌표
```

능력치는 노션 능력치 DB가 아직 비어 있어서 프로토타입 최소셋만 정의한다 — 공통 `max_hp`/`speed`, 아군 `max_sp`. 확장은 다음 이터레이션.

### 9.1 초기 카드셋 (5종, 아군 전용)

| id | 이름 | SP | 타입 | 형태 | 사거리 | 데미지 |
|---|---|---|---|---|---|---|
| `strike` | 베기 | 1 | MELEE | SINGLE | 1 | 6 |
| `cleave` | 횡베기 | 2 | MELEE | SWEEP | 1 | 4 |
| `shoot` | 사격 | 1 | RANGED | SINGLE | 3 | 4 |
| `volley` | 일제사격 | 2 | RANGED | SWEEP | 4 | 3 |
| `piercing_shot` | 관통사격 | 2 | RANGED | PIERCE | 3 | 5 |

숫자는 플레이해보고 조정할 출발점이지 확정값이 아니다.

## 10. 클래스 구성

| 클래스 | 종류 | 책임 |
|---|---|---|
| `Unit` | RefCounted | 스탯, 위치, 팀, HP, block. 아군이면 SP와 4개 존, 드로우·버리기 |
| `BattleState` | RefCounted | 양 진영 그리드, 전체 유닛, 라운드/이니셔티브 진행, 카드 사용·적 행동 해결, 데미지 적용, 승패 판정, RNG 보유 |
| `TargetResolver` | RefCounted (static 함수 모음) | 거리 계산, 블로킹 판정, 유효 타겟 목록, 광역 패턴 전개. 아군 카드와 적 공격이 공용으로 쓴다 |
| `EnemyBrain` | RefCounted | 적 차례에 공격/방어/휴식 중 하나를 결정 (8.3) |
| `BattleController` | Node | 입력 ↔ 규칙 ↔ 화면 중계 |

`Unit` 하나가 아군·적군을 겸하되 카드 관련 필드는 아군일 때만 채워진다. 런타임 클래스까지 둘로 쪼개면 이니셔티브 큐와 데미지 처리가 매번 분기해야 해서 오히려 지저분해진다. 대신 데이터(`AllyData`/`EnemyData`)는 타입으로 갈라 두어 잘못된 조합이 애초에 안 만들어지게 한다.

`BattleState`가 카드 사용 해결까지 들고 있는데, 효과 종류가 늘어나면 이 파일이 먼저 비대해질 것이다. 그 시점이 3장에서 말한 효과 엔진을 도입할 신호다.

## 11. 표현 레이어

플레이 가능한 최소 수준만 만든다. 2.5D는 다음 이터레이션이다.

- 진영 그리드 2개: `GridContainer` + 셀마다 `Panel`(이름 / HP / block, 아군은 SP도)
- 손패: `HBoxContainer` + 카드당 `Button` (이름 / SP 비용 표시). 아군 차례에만 표시
- 적 차례에는 그 적이 고른 행동(공격/방어/휴식)을 로그에 남긴다
- 턴 순서 표시: 이니셔티브 큐를 나열하는 `Label`
- 전투 로그: `RichTextLabel`
- 조작: 카드 버튼 클릭 → 유효 타겟 셀 하이라이트 → 셀 클릭 시 사용. 다시 카드 클릭 시 선택 해제.
- "차례 종료" 버튼

화면 갱신은 `BattleState`가 발생시키는 시그널을 `BattleController`가 받아서 처리한다. 규칙 코어가 노드를 직접 만지는 경로는 두지 않는다.

## 12. 테스트 전략

```
godot --headless --path <프로젝트> --script res://tests/run_tests.gd
```

이 방식이 실제로 동작함은 설계 단계에서 확인했다 (Godot 4.7.2, exit code 0).

- `tests/run_tests.gd` — `SceneTree` 상속. 테스트 파일들을 실행하고 실패 시 exit code 1로 종료.
- `tests/test_*.gd` — 각각 `RefCounted`. `run()` 에서 케이스 실행.
- 규칙 코어에 Node 의존이 없으므로 씬 없이 전부 검증 가능하다.

반드시 덮어야 할 것:

1. 좌표/거리 — 같은 크기, 다른 크기(홀↔짝 포함) 진영에서의 횡거리·종거리·reach
2. 블로킹 — 전열이 막는 경우/뚫리는 경우, 전열 유닛 사망 후 후열이 노출되는 경우
3. 광역 — PIERCE/SWEEP 전개, 1차 타겟만 사거리·블로킹 검사한다는 규칙, 패턴이 대상 진영을 벗어나지 않는지
4. 덱 — 드로우, 덱 고갈 시 묘지 리셔플, 덱·묘지 둘 다 빈 경우, 차례 종료 시 손패 버리기
5. 턴 — 이니셔티브 정렬과 동점 처리, 사망 유닛 차례 건너뛰기, 아군/적군 차례 구조가 다르다는 점
6. SP — 부족한 카드 사용 거부, 차례 시작 시 회복
7. block — 흡수 후 잔여 데미지만 HP에 적용, 흡수량만큼 감소, 자기 차례 시작 시 0으로 초기화
8. 적 행동 — 공격/방어/휴식 각각의 효과, 8.3 선택 규칙이 세 분기 모두 결정론적으로 갈리는지, 적 공격이 아군 카드와 같은 타겟팅 규칙을 따르는지
9. 승패 판정

**알려진 잡음:** `MCPRuntime` 오토로드가 테스트 실행 시에도 떠서 7777 포트를 잡고 로그를 남긴다. 게임 인스턴스가 이미 떠 있으면 포트 충돌 메시지가 찍히는데 테스트 결과에는 영향이 없다. 거슬리면 나중에 오토로드에 환경변수 가드를 넣는다.

## 13. 구현 순서

TDD로 진행한다. 각 단계마다 테스트를 먼저 쓴다.

1. 테스트 러너 골격
2. 데이터 Resource (`CardData`, `UnitData`, `AllyData`, `EnemyData`, `EncounterData`, `UnitPlacement`) + 초기 카드셋 .tres
3. `Unit` — 스탯, HP/block 데미지 처리, 아군 존과 드로우/리셔플/버리기
4. `TargetResolver` — 거리, 블로킹, 광역 전개
5. `BattleState` — 유닛 배치, 카드 사용 해결, SP, 승패
6. 이니셔티브 턴 진행 (아군/적군 차례 구조 분기)
7. `EnemyBrain` — 공격/방어/휴식
8. `BattleController` + 최소 UI 씬
9. 실제로 플레이해보고 숫자 조정

## 14. 미결정 사항

- 카드 수치 밸런스 (9.1은 출발점일 뿐)
- 적 행동 3종(공격/방어/휴식)은 **임시 테스트용**이다. 노션 기획의 적 설계가 확정되면 교체 대상.
- 적 수치(`block_amount`, `rest_heal`, `REST_THRESHOLD`)도 아직 근거 없는 출발점이다.
- 진영 그리드의 실제 기본 크기 — "다양하게" 라는 것만 정해졌다. 초기 조우는 아군 3×3 / 적군 3×3 으로 두고 크기가 다른 조우를 테스트 케이스로 함께 만든다.
- 유닛이 이동할 수 없으므로 이번 스코프에서 위치는 전투 내내 고정이다. 이동 카드가 들어오는 다음 이터레이션에서 위치 변경 API가 필요해진다.
